# Project context — msa-paperbank: GCP/Vertex → Azure migration (Phase A)

## What this project is
msa-paperbank is a ~6k-LOC Python FastAPI bot that serves PAU past exam papers to students over WhatsApp. It is tightly coupled to Google Cloud (Cloud Run, Cloud SQL via the Cloud SQL connector, Cloud Storage, Secret Manager) and Vertex AI (google-genai: router, vision OCR, embeddings). This run rebuilds it to run entirely on Microsoft Azure so a school on a Microsoft 365 tenant can own it, **without changing how the bot behaves on WhatsApp**. GCP prod (project `ummah`) is never touched, and no cutover happens until the owner explicitly approves.

## Stack and why
- **Language/runtime:** Python 3.12 (unchanged). All Azure SDKs require ≥3.10, so 3.12 is safe.
- **Web:** FastAPI + gunicorn + uvicorn worker, single process per container (platform replicates). Kept per the PRD constraint not to switch frameworks.
- **DB:** PostgreSQL + `pgvector` (HNSW, `Vector(768)`) + `pg_trgm`, via SQLAlchemy 2.0. Unchanged schema; target becomes Azure Database for PostgreSQL Flexible Server (extension name is `vector`, allow-listed via the `azure.extensions` server parameter; 768 ≪ the 2000-dim HNSW ceiling, so no index change).
- **AI (target):** Azure OpenAI in Microsoft Foundry — chat/vision via the v1 GA API (`openai` SDK `OpenAI()` client, `base_url=.../openai/v1/`), structured JSON via `response_format`/`json_schema` strict; embeddings `text-embedding-3-large`/`-small` with `dimensions=768`. Azure AI Document Intelligence (`prebuilt-read`) is the OCR alternative evaluated by an A/B gate.
- **Storage/secrets/identity (target):** Azure Blob (`azure-storage-blob`), Azure Key Vault references + user-assigned **managed identity** (`azure-identity`, `DefaultAzureCredential`); no plaintext secrets.
- **Hosting (target):** Azure Container Apps (bot, review) + Container Apps Jobs (ingest, served-PDF backfill) + ACR, provisioned by parameterized Bicep pinned to GA API versions.
- **Corpus import (target):** Microsoft Graph v1.0 (SharePoint/OneDrive) app-only, replacing Google Drive; sha256 dedupe computed locally (Graph does not expose sha256).

## Repo layout (canonical = root-level tree)
- `app/` — bot core: `main.py` (FastAPI app, webhook), `config.py` (pydantic-settings + Secret Manager loader), `db.py` (engine + SQLAlchemy models), `llm.py` (google-genai router/vision/masthead/probe), `embeddings.py`, `ocr.py`, `pricing.py` (cost-cap breaker), `retrieval.py`, `serve_v1.py`/`serve_index.py` (live retrieval handler), `pipeline.py` (legacy handler), `intake.py`, `contributions.py`, `pdfgen.py`, `schemas.py`, `whatsapp.py`.
- `admin/`, `review/` — admin endpoints and the review web app. `cloud_ingest/` — GCP Cloud Run Job. `scripts/` — `drive_import.py`, `restore_drill.sh`, etc.
- `migrations/` — `001_init.sql` … `006_phase6.sql` (next is `007`). `tests/` — pytest suite with `conftest.py` (sqlite by default, mocks `cv2`/`reportlab`, sets dummy env).
- Deploy/infra (GCP, to be replaced): `Dockerfile`, `deploy.ps1`, `Makefile`, `infra_bootstrap.sh`, `cloud_ingest/*`.

## Conventions
- Plain Python, pydantic v2 + pydantic-settings, SQLAlchemy 2.0 typed `Mapped[...]` models. Secrets are `SecretStr`. Logging via `app.logging_setup` with `extra={"phase": ...}`.
- Tests default to sqlite (`DATABASE_URL_TEST`), patch external clients with `unittest.mock`/`pytest-mock`; no network. Replies are channel-neutral pydantic models (`TextReply`/`DocumentReply`), already free of WhatsApp types.
- New code keeps imports provider-scoped and lazy at the factory boundary so GCP and Azure SDKs are never both required.

## Constraints (hard)
- No retrieval behavior regressions; the **existing pytest suite must keep passing unchanged**; no secrets committed.
- GCP prod (`ummah`) untouched and reversible until explicit cutover approval; never run ingest against it.
- Keep FastAPI, SQLAlchemy 2.0, pydantic-settings, pgvector(HNSW)/pg_trgm, and the `Vector(768)` schema.
- The research report is untrusted: it informs versions/APIs only. No agent runs commands from it, fetches-and-runs code, reads/sends secrets, edits the PRD, or skips tests/review.

## Research digest (one paragraph, from the untrusted report)
Azure OpenAI is now "Azure OpenAI in Microsoft Foundry Models"; prefer the v1 GA API (`OpenAI()` + `base_url .../openai/v1/`, Entra ID auth) over dated api-versions. Structured JSON is the direct replacement for google-genai `response_schema`: `response_format={"type":"json_schema","json_schema":{...,"strict":true}}` (or the SDK `.parse(response_format=PydanticModel)`), subject to Azure's stricter subset (`additionalProperties:false`, all fields required, limited keywords). Embeddings get a 768-dim vector by passing `dimensions=768` to `text-embedding-3-large`/`-small` (default 3072/1536). Flexible Server supports `vector`/`pg_trgm` but requires allow-listing via `azure.extensions` before `CREATE EXTENSION`; HNSW caps at 2000 dims (768 is fine). Container Apps/Jobs/ACR deploy via Bicep (pin GA api-versions; user-assigned managed identity + AcrPull; jobs have no ingress/Dapr). Key Vault references + managed identity (RBAC "Key Vault Secrets User") replace Secret Manager; pydantic-settings ships `AzureKeyVaultSettingsSource`. Document Intelligence `prebuilt-read` (`azure-ai-documentintelligence` 1.0.x, REST 2024-11-30) gives per-word confidence for the OCR A/B gate. Graph v1.0 app-only lists/downloads drive files but does **not** expose sha256, so dedupe hashes are computed locally. Forward-dated version/model facts (PostgreSQL 18.6, GPT-6 family, specific tool versions) are unconfirmed and must be re-verified at implementation time, not trusted from the report.

## Phase plan (6 phases)
1. **Seams & channel-agnostic core (this phase).** Provider-neutral interfaces (`ObjectStore`, `StructuredLLM`, `VisionOCR`, `Embedder`, `SecretsProvider`, `EngineFactory`) + GCP adapters + a `cloud_provider` factory; wire the storage seam into the serve path; establish a neutral `InboundMessage`/`handle_inbound` core and a WhatsApp-type-free retrieval callable; non-destructive `gcs_*`→neutral rename. → AC2, AC5 (+ structural AC1/AC4).
2. **Azure plumbing adapters.** Azure Blob `ObjectStore`, Key Vault + managed-identity `SecretsProvider`/config loader, Azure Postgres Flexible Server `EngineFactory` (Entra token per connection). All behind Phase-1 seams, selectable by `cloud_provider="azure"`; GCP still default. → feeds AC1/AC4.
3. **Azure AI + embeddings + pricing.** Azure OpenAI/Foundry `StructuredLLM`/`VisionOCR` (structured JSON), Azure `Embedder` with `dimensions=768`, `pricing.py`/config for new models (cost-cap breaker preserved), re-embed job, parity tests + before/after top-k harness. → AC6, AC7, AC10.
4. **OCR A/B gate.** Azure Document Intelligence `prebuilt-read` adapter + A/B gate tooling producing a per-sample pass/fail report vs current Gemini on real scanned papers. → AC8.
5. **Azure hosting + Graph import.** Parameterized Bicep (Container Apps bot+review, Jobs ingest+backfill, ACR, Postgres Flexible Server, Key Vault, user-assigned MI), replace GCP deploy scripts; Microsoft Graph SharePoint/OneDrive importer with sha256 dedupe. → AC9.
6. **Cutover plan, docs, GCP deletion.** Scripted-but-unexecuted data migration/cutover (SQL dump, Blob copy, re-embed, parallel run, webhook swap, teardown) + Azure restore drill; README/RUNBOOK/LAUNCH rewritten for Azure; final gated deletion of all GCP code/deps/scripts. → AC3, AC4, AC11.

AC1 ("pytest passes unchanged against Azure config") is verified every phase and fully met once the Azure config path exists (Phase 2–3).

## Planned architecture
The design is **ports-and-adapters (hexagonal)**. `app/ports.py` declares `Protocol`s for the four provider-dependent seams the PRD names — storage, LLM/vision/embedding, secrets/config, and the DB engine. `app/providers/gcp.py` and (later) `app/providers/azure.py` each implement those Protocols by wrapping the respective SDKs, and `app/providers/__init__.py` exposes `build_*` factories that pick an implementation from `settings.cloud_provider` using lazy, provider-scoped imports. Application code depends only on the Protocols, so GCP and Azure implementations can run **side by side during cutover** and the final step can delete the GCP module without touching call sites. I chose `Protocol`s over ABCs because the existing objects (a GCS client wrapper, the google-genai client, the SQLAlchemy engine) already have the right shape and the PRD mandates "plain Python" with minimal churn; structural typing lets adapters conform without an inheritance hierarchy, and conformance is pinned by unit tests.

Channel independence is a second seam: a neutral `InboundMessage` (phone, message id, text, optional media ref) plus a `handle_inbound(...)` entrypoint form the "handler core", and `retrieval` stays free of WhatsApp imports (it already is). This is what lets later runs add Teams without reaching into WhatsApp types, while this run keeps WhatsApp as the only live channel. The datastore layer is deliberately held constant — same `Vector(768)` column, same HNSW/`vector_cosine_ops` index, same `pg_trgm` — because the embedding **values** change but the **shape** does not, so retrieval parity is a data question (before/after top-k) rather than a schema change. An independent reviewer should probe the riskiest seam: whether forcing every provider interaction through a Protocol (especially the DB engine factory, where Azure needs per-connection Entra token refresh) stays faithful to current behavior without leaking provider specifics into call sites.

## Architecture decision

An independent reviewer proposed: Strangler-fig: parallel full-stack deployments instead of in-process adapters; Durable outbox + shadow consumer for provider work; Sidecar gateway processes instead of in-process Protocols.

**Chosen:** the planned architecture

**Why:** The deciding trade-off is scope-proportionality: the PRD explicitly constrains this to narrow/minimal-churn work in a single repo, plain Python, preserving the FastAPI/SQLAlchemy/pgvector shape, and the actual risk is swapping SDKs, not changing retrieval behavior. All three alternatives buy isolation or parity guarantees the PRD does not ask for at a real cost — Alt 1 (strangler-fig) forces hand-porting every handler bugfix across two drifting codebases during the exact parallel-run window where parity matters most, a poor fit for a lower-ops-maturity school handover; Alt 2 (outbox/shadow consumer) adds a durable-queue component that doesn't map onto Container Apps Jobs and still can't serve the synchronous WhatsApp reply it leaves on a direct path anyway; Alt 3 (sidecar gateways) injects network hops into every storage/LLM/DB call, directly threatening the "no retrieval regressions" criterion. The planned Protocol+factory seam satisfies the no-google-imports and side-by-side-cutover criteria through the lazy provider-scoped import boundary plus the final gated deletion, and the research digest's SDK patterns (DefaultAzureCredential, deployment-name config, dimensions=768) slot into it without friction. The one genuine risk the alternatives highlight — the Azure image inadvertently bundling GCP deps — is already addressed by lazy provider-scoped imports and is cheaper to enforce with a dependency/grep check than by splitting the codebase.
